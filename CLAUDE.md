# Pinpoint

An AGLC4 (Australian Guide to Legal Citation, 4th ed) citation generator for law students. Next.js 14 App Router, TypeScript, Tailwind. GitHub remote: `github.com/rhyle-s/pinpoint` (`origin`, branch `main`); not deployed anywhere yet — see "Deployment" below.

## Architecture

- **`lib/citation-engine/`** — deterministic, pure-function citation formatting, one file per source type (`cases.ts`, `legislation.ts`, `journal-articles.ts`, `books.ts`, `reports.ts`, `research-papers.ts`, `websites.ts`, `other-legislative-material.ts`, `international-material.ts`, `other-sources.ts`). `treaties.ts` and `un-documents.ts` still hold the actual Treaty/UN Materials formatting logic, and `foreign-domestic.ts` holds all Foreign Domestic Sources formatting (Canada/NZ/UK/US/Hong Kong/Malaysia/Singapore/South Africa) — none of these three are independent `SourceType`s, `international-material.ts` is a thin adapter/dispatcher in front of all three; see the "International Material" convention below. `index.ts` dispatches on `SourceType` and exposes `generateCitationSync` (safe to call client-side for instant preview) and `formatItalics` (the single chokepoint that converts `*text*` markers to italics and straight quotes/apostrophes to typographic ones for actual display/copy).
- **`lib/citation-engine/validator.ts`** — a second pass using Claude to catch what the deterministic engine can't (AGLC4 rule text is embedded per source type in `RULES_BY_SOURCE_TYPE`, plus shared `BIBLIOGRAPHY_RULE`/`SUBSEQUENT_RULE` since those diverge from the per-type rules in ways worth stating once).
- **`lib/autofill/`** — three independent ways to populate fields, all funnelling into the same field-mapping/validation logic in `ai-extract.ts`:
  1. **URL paste** (`lib/autofill/index.ts` → `autofill()`) — routes by domain/pattern (AustLII, AU state legislation sites, CrossRef DOIs, PubMed PMIDs, or the generic AI-extraction fallback).
  2. **PDF upload** — parsed **entirely client-side** via `pdfjs-dist` (`lib/pdf-extract/client-extract.ts`); only a small text summary (title/author/subject/keywords/creator/producer + a ~2000-char page-1 snippet) is ever sent to `/api/autofill/pdf`. The file itself never reaches the server — this was a deliberate legal/privacy requirement, not just an implementation choice. See "PDF upload internals" below before touching this.
  3. **Paste text** — for sources Pinpoint can't fetch at all (login-gated databases like Lexis+/Westlaw — see `BLOCKED_DATABASES` in `lib/autofill/detect.ts`): student copies the citation details by hand, same extraction pipeline as the other two.
- **`Generator.tsx`** — the main client component. Tracks per-field "touched" state (`touchedFields`) so a fresh autofill can safely overwrite everything *except* what the student manually typed, while pinpoint fields are deliberately excluded from that protection (see `PINPOINT_KEYS`) since they identify a spot in *this* citation, not the source itself, and should never carry over between citations.
- **`lib/autofill/cross-type-map.ts`** — lets a student correct a wrong source-type guess by clicking a different tab (eg the app detected 'journal' but it's actually a book chapter) without losing what's already filled in. See "Cross-type tab switching" below.

## Non-obvious conventions (read before "fixing" these)

- **Typographic quotes**: `applyTypographicApostrophes` in `citation-engine/index.ts` is context-aware, not a blind `'` → `'` replace — it has to correctly open/close a straight-quoted phrase nested inside a title (eg `the 'black box'`), which a naive replace gets wrong.
- **Bibliography formatting** differs from footnote/subsequent in three ways, all deliberate: never uses "et al" (lists every author in full), only the *first* author's name is inverted to `Surname, Given`, and it ends with **no trailing full stop**. The AI validator didn't know this until `BIBLIOGRAPHY_RULE` was added — if it starts "correcting" a correct bibliography back to footnote style, that rule text is the first place to check.
- **Author names**: always full given names, never abbreviated to initials (`formatAuthorAGLC4` in `lib/autofill/utils.ts`). Sources like CrossRef sometimes hand back a stray full stop after a single-letter middle initial (eg `"Emily M."`) — `stripInitialFullStops` in `citation-engine/utils.ts` cleans this at render time, inside `formatAuthorList`/`formatBibliographyAuthorList`, so it's applied regardless of where the name came from.
- **Legislation pinpoints from a pasted URL**: NSW, Qld, and Tas run the same underlying platform (confirmed by matching generic `<title>` tags and identical URL structure) with a `#sec.N`-style fragment convention — `lib/autofill/au-legislation.ts` parses this directly from the URL string (no fetch needed). Deliberately **not** extended to Vic/WA/SA/ACT/NT, which run different, unverified platforms — guessing a pinpoint wrong is worse than leaving it blank, so those get a "please add manually" note instead via `finalizeAutofillResult` in `lib/autofill/utils.ts`.
- **AGLC4 rule-number confidence**: every rule number cited in the UI (`AGLC4 r X.X`) is asserted with reasonable confidence *except* the Conference/Research Paper/Thesis type, which cites `AGLC4 ch 7` only — the chapter is right, the general format is right, but the precise sub-rule numbering (conference papers vs theses may be separately numbered) hasn't been verified against the actual guide. Worth tightening if the user ever confirms the exact numbers.
- **Report author is usually an organisation, not a person.** `ReportFields.authors` (`citation-engine/types.ts`) takes the publishing body's own name exactly as it self-identifies (letterhead/copyright line/masthead) — 'Cisco', 'Woolworths Group', 'Australian Law Reform Commission'. The `ai-extract.ts` system prompt states this explicitly for `report`; before this was added, corporate/government reports either got no author at all or a wrong guess.
- **A report's title/documentType split follows a specific AGLC4 rule**, quoted verbatim in the `ai-extract.ts` system prompt: a document-type label that's *separate* from the real title (eg cover text '2025 Annual Report' above a distinct tagline) becomes the `documentType` ('Annual Report'), leaving only the tagline as the `title`; a label that *is* the title (eg cover text '2025 Sustainability Report' with nothing else) stays in the `title` ('Sustainability Report') and `documentType` takes the *generic* form ('Report', not 'Sustainability Report'). The same generic-form principle covers government policy documents (`documentType` 'Policy Document') and self-described white papers (`documentType` 'White Paper' — classified as `sourceType: 'report'`, *not* `'researchPaper'`, despite the name collision). `stripDuplicateYearFromTitle` (`lib/autofill/utils.ts`) is a code-level safety net for the same rule's year-handling — confirmed necessary in practice: the prompt alone still let a cover-page year ('Sustainability Report 2025') leak into the title on a real test.
- **Reports now carry a `url` field** (`ReportFields.url`, optional), rendered `<url>` after the pinpoint exactly like `WebsiteFields` — omitted from the subsequent reference, included in footnote/bibliography. Previously absent entirely, so a report fetched from a URL had no way to cite where it came from.
- **`newspaper` (AGLC4 r 7.11.2) is a separate source type from `website` (r 7.15)**, not a `documentType` variant of it, even though `newspapers.ts` is structurally almost identical to `websites.ts` (same quoted-title/italicised-publication-name/parenthetical/URL shape). The parenthetical is hardcoded to the literal word `'online'` plus the date — there's no print-edition variant, since only the electronic form was ever built. `ai-extract.ts`'s system prompt is the only thing distinguishing the two source types at extraction time: it looks for a journalistic byline ("By [Reporter Name]") and/or a recognisable news-outlet masthead name (often the segment after the ` - `/` | ` separator in the page's own `<title>` tag) to prefer `newspaper` over the generic `website` fallback. Confirmed on a real article that a page's `og:title` meta tag can lag behind an edited headline — the extractor is told to prefer the page's own `<title>`/`<h1>` text, which `extractPageContent()` in `ai-extract.ts` was already doing before this feature (a happy pre-existing accident, not something added for this).
- **`otherLegislativeMaterial` bundles five distinct AGLC4 ch 3 categories under one source type** (Bill r 3.2, Explanatory Material r 3.7, Gazette r 3.9.1, Court Practice Direction/Note, and Constitution r 3.6) — one interface (`OtherLegislativeMaterialFields`, a `subtype` discriminant plus each subtype's own optional fields) and one dispatcher file (`other-legislative-material.ts`), mirroring how `CaseFields`/`cases.ts` already bundle three case-citation shapes rather than three separate `SourceType`s. `otherLegislativeMaterialBadge()` (same file) names the specific sub-category in the UI (`CitationOutput.tsx`'s `badge` prop, set by `Generator.tsx`) — as specific as the data allows, eg the exact 'Practice Note' vs 'Practice Direction' rather than a generic label.
  - **Constitution delegates to `generateLegislationCitation` internally** rather than reimplementing the identical title/year/jurisdiction/pinpoint formula — a constitution (the bare Commonwealth 'Australian Constitution', or a state/territory's own constituting Act) is cited exactly like an ordinary Act. The bare Commonwealth Constitution is the one deliberate exception: no year, no jurisdiction bracket at all — achieved simply by leaving `constitutionYear` empty and `constitutionJurisdiction` `'none'`, the same mechanism `LegislationFields` already uses.
  - **A Bill's title/year/jurisdiction reuse the same `actTitle`/`year`/`jurisdiction` schema fields as ordinary legislation** in `ai-extract.ts` — the extractor is simply told never to italicise a Bill's title (r 3.2's one departure from r 3.1) and, for `explanatoryMaterial`, to also set `explanatoryLabel` to whichever of the four terms ('Explanatory Memorandum'/'Statement'/'Note'/'Notes') the jurisdiction itself uses.
  - **`au-legislation.ts`'s dedicated AU legislation domains (`legislation.*.gov.au`) also host Bills and their Explanatory Memoranda**, not just ordinary Acts, and forcing every fetch there down the `'legislation'` sourceType hint (as it did before this feature) would have silently italicised a Bill's title or mis-typed an Explanatory Memorandum as a bare Bill. Two layers handle this: `detectBillSubtype()` recognises a reliable URL-level signal where one exists (eg Queensland's own convention distinguishes `/bill.first/...` from `/bill.first.exp/...`, confirmed by direct testing) and routes straight to the hinted `'otherLegislativeMaterial'` path; everywhere else, `handleAuLegislation()` deliberately calls `aiExtractFromUrl()` with **no hint at all**, trusting the model's own content classification — confirmed necessary on a real Victorian Explanatory Memorandum served from an opaque content-hash filename with no textual signal in the URL whatsoever. Confirmed this doesn't regress ordinary-Act extraction (tested separately).
  - **`extractPdfText()` (`lib/pdf.ts`) samples both ends of a long PDF, not just the start** — many official documents (court practice directions/notes especially) place their own issuing/signing date in a signature block at the very end, confirmed on a real practice note where that date sat at character ~14078 of a 14094-character document. The last `TRAILING_SAMPLE_LENGTH` characters are appended as a labelled `[Document end]: ...` excerpt once the document exceeds the leading-text budget, at the cost of a little of that leading budget — a fetched-PDF-only fix (the client-side PDF-upload path, `client-extract.ts`, has its own separate, already-multi-region sampling strategy).
- **A book source extracts both whole-book and chapter fields at once, even though `bookType` always defaults to `'book'`.** `BookFields` (`citation-engine/types.ts`) has always had a `bookType: 'book' | 'chapter'` discriminant with `books.ts`/`BookForm.tsx` fully supporting both — but `ai-extract.ts` never populated the chapter-only fields (`chapterAuthors`, `chapterTitle`, `editors`, reusing `title`/`startingPage`), so switching a book to "Book chapter" in the UI produced a blank/broken citation. The `'book'` case in `mapFieldsToSourceType` now populates both sets unconditionally, and `bookType` stays hardcoded to `'book'` as the default — a student who manually flips the "Book type" selector gets a correctly pre-filled chapter citation immediately, without re-extracting. The system prompt teaches the model to invert a Surname-first citation line (a repeating ProQuest/Ebook Central footer watermark is the most common source of this, eg `'Groves, Matthew, and H. P. Lee.'` → editors `['Matthew Groves', 'H P Lee']`) and to derive `startingPage` from a running page-footer/header number rather than the PDF excerpt's own page 1.
  - **This exposed a real validator bug, not just a missing-fields gap**: once `chapterAuthors`/`chapterTitle`/`editors` started arriving non-empty alongside `bookType: 'book'`, the AI validator — which receives the full raw fields object, not just the rendered citation — started "correcting" the correct whole-book citation into chapter format on its own initiative, since its `book` rule text described both formats without saying which one governs when both sets of fields are present. Fixed by adding an explicit instruction to `RULES_BY_SOURCE_TYPE.book` in `validator.ts`: `bookType` is authoritative, and the chapter-only fields must be ignored for validation whenever `bookType` is `'book'`. The same "check the validator's embedded rule text too, not just the deterministic engine" pattern as the Practice Direction italics bug above.
  - **It also exposed a second, separate bug in `Generator.tsx`'s touched-field tracking**: manually flipping the "Book type" selector to "Book chapter" marks `bookType` touched exactly like typing into any free-text field (`markFieldsTouched('book', changedKeys(...))` diffs the whole fields object generically), so a *subsequent, unrelated* PDF upload kept re-using the previous book's `'chapter'` selection instead of resetting to the fresh autofill's `'book'` default — confirmed live by uploading the same chapter PDF twice with a manual toggle in between. `bookType` behaves like a pinpoint field in this one respect (it must never carry over from whatever the student was previously citing) despite not literally being a pinpoint, so it has its own `CLASSIFICATION_KEYS` map alongside `PINPOINT_KEYS`, both excluded from touched-field protection in `protectedKeysForAutofill`. Worth checking for the same shape of bug if another source type ever gains a similar student-toggleable sub-type discriminant.
- **`internationalMaterial` bundles Treaty, UN Materials, and Foreign Domestic Sources under one badge-driven source type**, at the user's explicit request, mirroring the exact `otherLegislativeMaterial` pattern above: one interface (`InternationalMaterialFields`, a `subtype: 'treaty' | 'unDocument' | 'foreignDomestic'` discriminant plus every subtype's own optional fields flattened together), one dispatcher file (`international-material.ts`), and `internationalMaterialBadge()` naming the detected subtype in the UI. Deliberately *not* a rewrite of the underlying Treaty/UN Materials logic — `treaty`/`unDocument` were previously two independent, already-tested `SourceType`s (`treaties.ts`/`un-documents.ts`), and the merge keeps both files completely unchanged, just no longer independently reachable as a `SourceType`: `international-material.ts`'s `toTreatyFields`/`toUNDocumentFields` build a proper `TreatyFields`/`UNDocumentFields` object from the merged shape and call the existing functions directly, so the citation output for both is byte-for-byte identical to before the merge (verified: same ICESCR/UDHR test fixtures produce the same footnote/bibliography strings). The UN Materials badge/label is a deliberate rename from the old "UN Document" — the underlying `subtype` value is still the string `'unDocument'` (internal key, unchanged, still shared with `treaties.un.org`/OHCHR-facing code); only the user-facing text changed.
  - **`Generator.tsx`'s `CLASSIFICATION_KEYS` needed `internationalMaterial: ['subtype']` added**, for the exact same reason `book` needed `bookType` there (see the Book chapter bug above): without it, a student who manually flips the Category selector to "Foreign Domestic Sources" would find a later, unrelated autofill stuck on that selection instead of resetting to the fresh result's own detected subtype — `subtype` is a classification field, not something that should carry over from whatever the student was previously citing. Added `otherLegislativeMaterial: ['subtype']` to the same map while here, since it had the identical latent gap and had just never been hit in practice.
  - **`title`/`pinpoint`/`footnoteNumber`/`shortTitle` are shared field keys across all three subtypes** (all three subtypes' own field shapes already used `title` and `pinpoint`), which is a deliberate convenience — switching the Category selector carries the same title across Treaty ↔ UN Materials ↔ Foreign Domestic Sources rather than blanking it, since it's very often still the correct title after a subtype correction. The flip side (also correct, not a bug): once the student has typed into `title` for *any* subtype, `Generator.tsx`'s ordinary touched-field protection keeps protecting it from a later, unrelated autofill exactly the same way it always has for every other field — this isn't new behaviour introduced by the merge, just now visible across what used to be two separate tabs with two separate `touchedFields` sets.
  - **Foreign Domestic Sources (`lib/citation-engine/foreign-domestic.ts`) covers 8 of AGLC4 Part V's 11 jurisdictions with real, verified citation formats** — Canada, New Zealand, the UK, the US, Hong Kong, Malaysia, Singapore, and South Africa — built from the actual AGLC4 guide text (Melbourne Law School's own PDF, downloaded and read directly; the primary `law.unimelb.edu.au` host is Cloudflare-blocked the same way other AGLC4-related domains already documented in this file are, but a UTS mirror worked). **China, France, and Germany are deliberately not covered** — AGLC4 cites those in a fundamentally different shape (original-language text with bracketed English translations, guillemets `«»`, no italics on non-English titles) that doesn't fit this Latin-script field/form pattern at all; a separate follow-up, same as how Foreign Domestic Sources itself was originally deferred.
    - **A nested discriminant, one level deeper than `otherLegislativeMaterial`'s pattern**: `foreignCountry` (which of the 8 jurisdictions) then `foreignCategory` (case/legislation/delegatedLegislation/legislationSessionLaw/constitution — which categories are valid varies per country, enforced by `ForeignDomesticForm.tsx`'s `CATEGORIES_BY_COUNTRY` map filtering the Type `<select>`'s options). `Generator.tsx`'s `CLASSIFICATION_KEYS.internationalMaterial` had to grow from `['subtype']` to `['subtype', 'foreignCountry', 'foreignCategory']` for exactly the same "must never carry over from a stale prior selection" reason `subtype` itself needed adding — confirmed live: without this, correcting a wrong country guess and then running an unrelated autofill left the country/category stuck.
    - **Case citations for 7 of the 8 countries reuse the exact same "chapter 2" bracket-style logic already built for Australian cases**, since AGLC4 literally says Canadian/NZ/UK/Hong Kong/Malaysian/Singaporean/South African cases are all "cited in accordance with chapter 2" — `foreign-domestic.ts`'s shared `chapterTwoCase()` helper calls the existing `getBracketType()` (`report-series.ts`), extended (additively, no Australian entries touched) with each country's own report-series abbreviations (eg `SCR`/`FC`/`Ex CR` square for Canada, `DLR` round; `NZLR`/`NZAR`/`NZFLR` square, `NZBLC`/`NZCPR`/`PRNZ` round for NZ; `SA` square for South Africa). The US is the one genuine structural exception (r 25.1): case name takes a trailing comma, volume precedes the report series, and jurisdiction/court sits in a final parenthetical with the year — omitted entirely for the US Supreme Court — so it gets its own `formatUSCase()` rather than sharing `chapterTwoCase()`.
    - **Malaysia's `MLJ` report series is genuinely date-dependent, not just table-driven**: AGLC4 r 20.1.2 states it switched from volume-organised (round brackets) to year-organised (square brackets) in 1966 — `formatMalaysiaCase()` branches on the case's own year directly rather than using the static `getBracketType()` lookup, since a single abbreviation maps to two different bracket styles depending on date. Confirmed against both of AGLC4's own worked examples (a 1964 MLJ case, round; a 2009 one, square).
    - **Legislation pinpoint comma placement genuinely differs by country, confirmed by AGLC4's own worked examples, not assumed** — Canada (r 15.2.5), New Zealand, and the UK (r 24.2.5) each have an explicit "pinpoint preceded by a comma" sub-rule; Malaysia, Singapore, and South Africa have no such sub-rule and their own examples confirm no comma (eg `'Copyright Act 1987 (Malaysia) s 7.'`, not `'..., s 7.'`) — caught by writing the test suite directly against AGLC4's real examples rather than inventing plausible-looking fixtures, which is what surfaced this as a real bug in the first draft (all three had been wired through the comma-prefixed `formatPinpoint()` uniformly). `bareSpacePinpoint()` is the fix for those three; Canada/NZ/UK keep using the ordinary comma-prefixed `formatPinpoint()`.
    - **The validator's global `SUBSEQUENT_RULE` ("legislation subsequent references don't use `(n X)`") only ever meant the domestic Australian `'legislation'` SourceType** (AGLC4 r 3.1's own subsequent-reference convention), but its original wording said just "for legislation specifically" with no scoping — confirmed as a real bug live: a Canadian/UK Foreign Domestic Sources legislation citation, which correctly uses the ordinary `(n X)` pattern like every other `internationalMaterial` subtype, was being wrongly "corrected" by the AI validator to the Australian-only style, flipping a genuinely-correct citation to "Corrected" status. Fixed by explicitly scoping the rule's text to the one domestic source type and stating the `(n X)` pattern applies to Foreign Domestic Sources legislation too.
    - **Autofill is wired for Canada and the UK only** (the two the user gave concrete worked URL examples for) — `detect.ts`'s `FOREIGN_DOMESTIC_DOMAINS` recognises `laws-lois.justice.gc.ca` (Canada legislation), `decisions.scc-csc.ca` (Canada cases, the Supreme Court of Canada's own site), and `legislation.gov.uk` (UK legislation, all four jurisdictions) as a new `'foreign-domestic-url'` input type, routed to `aiExtractFromUrl(url, 'internationalMaterial')` — a strong `sourceType` hint, same mechanism `au-legislation.ts` already uses. Country and category are **never** trusted to the model — `ai-extract.ts`'s `mapFieldsToSourceType` determines both 100% deterministically from the URL string itself (which it already receives), the same "merge in what's already known afterward" pattern `au-legislation.ts` uses for `billJurisdiction`. UK jurisdiction (`UK`/`NI`/`Scot`/`Wales`) is read directly from the URL path segment right after the domain (`ukpga`/`nia`/`asp`/`mwa`, plus the `uksi`/`nisr`/`ssi`/`wsi` delegated-legislation equivalents for future use) via `detectUKJurisdictionFromUrl()` — exactly the same shape as `au-legislation.ts`'s `detectBillSubtype()`. Only the genuinely page-content-dependent fields (statute volume type, chapter/section numbers, jurisdiction abbreviation letters) are left to the model, taught via new `SYSTEM_PROMPT` guidance blocks. NZ/US/Hong Kong/Malaysia/Singapore/South Africa deliberately have no autofill wiring yet — manual entry only, same as `foreignDomestic` as a whole originally shipped.
    - **Canada legislation autofill no longer goes through the AI at all — `lib/autofill/canada-legislation.ts` + `canada-legislation-parse.ts` parse the citation directly, after two rounds of real, user-caught bugs in the AI-based approach.** First report: `laws-lois.justice.gc.ca`'s own URL slug isn't always the AGLC4-citable chapter (most Acts' slug and real chapter coincide — Privacy Act: slug `P-21`, real chapter `P-21` — but an Act added via one of the five *Supplements* to the 1985 consolidation, eg the Income Tax Act, has a plain numeric chapter plus a separate supplement number, `RSC 1985, c 1 (5th Supp)`, completely unlike its slug `I-3.3`) — the extraction prompt's own example list (`'P-21'`, `'C-46'`) looked enough like a URL slug that the model pattern-matched the slug itself instead of reading the page. Fixed that round by rewriting the prompt and adding the missing `canadaSessionOrSupp` schema field — but a second, harder report (`Y-1.5`, the Youth Criminal Justice Act) showed that fix was papering over a deeper problem: **the page's own citation heading — `'Title (Citation)'` — sits inside a `<header>` element that `ai-extract.ts`'s shared `extractPageContent()` strips out entirely as generic site-navigation chrome**, so the model was never shown the real citation on *either* page, for *any* Act on this site. The Income Tax Act round happened to come out right anyway — its citation is famous enough that the model produced it from background knowledge, not extraction — while the Youth Criminal Justice Act (less well-known) got a confidently wrong, hallucinated one instead. Same root cause, radically different visibility, which is exactly why "the one test case I tried now looks right" isn't enough confirmation for an LLM-extraction fix — a plausible-looking correct answer and a genuinely-extracted one are indistinguishable from the output alone. Direct testing confirmed the `'Title (Citation)'` heading is reliably present and parseable in the raw HTML across every Act tried (`P-21`, `C-46`, `I-3.3`, `Y-1.5`), so the real fix bypasses the AI for this site entirely: `handleCanadaLegislation()` fetches the page itself, `extractCanadaLegislationCitation()`/`parseCanadaCitationLine()` parse the citation line directly with a regex, and only pages that don't match the expected shape fall back to the AI-hinted path as a safety net — the same "never trust an LLM to reproduce a fact that can just be read directly" precedent as `known-treaties.ts`/`known-ohchr-instruments.ts`. `detect.ts` now routes `laws-lois.justice.gc.ca` to its own `'canada-legislation'` input type, separate from `decisions.scc-csc.ca`/`legislation.gov.uk`'s shared `'foreign-domestic-url'` AI-hinted route (those two are unaffected — their own content isn't hidden the same way). The parsing functions are kept in `canada-legislation-parse.ts`, deliberately without a `'server-only'` import (unlike `canada-legislation.ts`, which does the actual fetching), so they stay directly unit-testable — `'server-only'` breaks under the vitest test environment, which is also why `au-legislation.ts`/`ai-extract.ts` have no test files of their own. This new direct-fetch path also needed its own copy of `aiExtractFromUrl`'s timeout (`FETCH_TIMEOUT_MS`) and size-guard (`MAX_FETCH_BYTES`, see below) protections — both now exported from `ai-extract.ts` for reuse — since it fetches independently rather than going through that function for its primary attempt.
    - **UK legislation.gov.uk got the same "AI-based extraction is fragile, deterministic parsing is right" treatment as Canada, once asked to test it — plus its own italics/duplicate-year bugs the Canada round didn't have.** Unlike Canada, legislation.gov.uk's own citation heading (`'You are here:<Category><Year> <c./asp/nawm/No.> <Number>'`, eg `'You are here:UK Public General Acts2023 c. 50'`) *does* survive the shared AI-path's header/nav/footer stripping — but only fits inside the ~4000-character extraction budget by a comfortable-but-not-huge margin (roughly half the budget is wasted on this site's own search-form dropdown first), and the AI-hinted path never distinguished ordinary legislation from delegated legislation (SI/SR) by URL, always guessing `'legislation'`. Confirmed reliably parseable directly across every UK/NI/Scot/Wales example and a delegated-legislation example, so `lib/autofill/uk-legislation-parse.ts` + `uk-legislation.ts` bypass the AI entirely, mirroring Canada's architecture exactly (pure parsing module without `'server-only'`, kept unit-testable; server-only orchestration with the same timeout/size guards, exported from `ai-extract.ts` for reuse). `detect.ts` routes `legislation.gov.uk` to its own `'uk-legislation'` input type.
      - **`formatUKLegislation`/`formatUKDelegatedLegislation` never stripped a leading 'The' at all**, unlike Canada's formatter — a live example (`'The Fertilisers (Amendment) Regulations 1998'`, legislation.gov.uk's own `<title>` tag) confirmed the site genuinely includes it for at least some instruments. Fixed by applying the same `stripLeadingThe()` helper Canada already used.
      - **A genuinely confirmed-live duplicate-year bug (`'Fertilisers (Amendment) Regulations 1998 1998'`) was intermittently masked by the AI validator "correcting" it — but only in some cases, not others**, which is exactly why it wasn't obvious at first: legislation.gov.uk's own `<title>` tag already includes the year as part of the Act's/instrument's own name (matching AGLC4 r 24.2.1's own convention that the year is part of the title), but `ForeignDomesticForm.tsx`/`foreign-domestic.ts` treat title and year as two separate fields the formatter glues back together itself — so populating both independently duplicated it. One test of the same URL showed the AI validator silently fixing it (`'AGLC4 verified ✓'` even though the raw client-side citation was already wrong); a second, structurally identical test of a different URL didn't get the same "luck" and showed the raw duplicate. Fixed at the source with `stripTrailingYear()` (the same helper `au-legislation.ts`/`ai-extract.ts` already use for this exact "title already has the year baked in" shape) in `uk-legislation.ts`, rather than continuing to rely on the validator to catch it — a probabilistic AI safety net silently patching over a routine, deterministic formatting bug is not something to build on, even when it happens to work.

## Known external limitations (don't try to "fix" these without new info)

**Genuine Cloudflare bot challenges** (`cf-mitigated: challenge` header, confirmed by direct `curl` testing) — no User-Agent trick fixes these, and building a real JS-challenge solver is out of scope:
- `austlii.edu.au` (both cases and legislation)
- `legislation.nsw.gov.au`, `legislation.sa.gov.au`
- `supremecourt.nt.gov.au`
- `fedcourt.gov.au`
- `dl.acm.org`
All of these degrade gracefully to a fallback that fills whatever's derivable from the URL alone (jurisdiction, a pinpoint parsed from the fragment) and suggests the PDF-upload or paste-text alternative (`TRY_ALTERNATIVE_INPUT_SUGGESTION` in `lib/autofill/utils.ts`).

**`legislation.govt.nz` is now AWS-WAF-blocked too — a genuine regression in the external site, found during a full-project autofill audit (every source type, real URLs, both previously-tested and brand new ones).** Every real Act URL tried returns `HTTP 202`, an empty body, and `x-amzn-waf-action: challenge` — the identical signature already documented above for EUR-Lex — regardless of User-Agent, confirmed against multiple real Acts. This breaks `nz-legislation.ts`/`nz-legislation-parse.ts`'s own dedicated, previously-working deterministic route (built specifically because a real bug was once found there — see the international-material history below). No Cellar-style unblocked backdoor is known for this site the way there is for EUR-Lex; it currently falls through to the generic AI path, which naturally fails the same way and returns the ordinary "could not extract" message. Left as an external limitation to monitor rather than "fixed" — there's nothing on Pinpoint's side to fix until an alternative data source turns up.

**`decisions.scc-csc.ca` (the Supreme Court of Canada's own decisions site) has NO citation data anywhere in a case-detail page's server-rendered HTML at all — traced all the way down, not assumed.** Its case pages (a fully client-rendered "Decisia" CMS) load the real judgment via a same-origin iframe request (`.../item/<id>/<docId>/res.do`) — but that request itself, checked directly (both via a plain fetch and via a real browser session's own network capture), returns only CSS, never the actual document text or any citation metadata (year, volume, SCR page, judge). This used to be routed through the generic AI-extraction path with an `'internationalMaterial'` hint (`FOREIGN_DOMESTIC_DOMAINS` in `detect.ts`), guaranteed to fail every single time with no explanation — `index.ts`'s `'foreign-domestic-url'` case now short-circuits with an honest, specific message instead (mirroring the AustLII/SSRN pattern), pre-filling `foreignCountry: 'Canada'`/`foreignCategory: 'case'` so the student lands on the right form to fill in by hand. Worth revisiting only if a real, working data source for this site (an authenticated API, a different endpoint) is ever found.

**A stale URL in this app's own bundled worked example, not a real site block — confirmed by chasing it down, not assumed.** `http://www.hcourt.gov.au/justices/current/justice-james-edelman` (used in `lib/guide-content.ts`'s own website worked example) now 404s — the High Court's site restructured its URLs; the same content now lives at `https://www.hcourt.gov.au/justices/current-justices/hon-justice-james-edelman-ac`, which autofills correctly. Worth updating the guide's own example URL to the new one at some point, though the underlying autofill logic itself was never broken.

**`laws-lois.justice.gc.ca` genuinely serves large Acts very slowly, not just "large"** — confirmed by direct testing, not assumed: its `'FullText.html'` view embeds an entire Act including every schedule, so page size scales with the Act's length (the Income Tax Act, I-3.3, is 12MB+ — note its URL slug 'I-3.3' is the site's own catalogue identifier, not its real citation chapter, see the `canadaChapter` note below), and the site also takes a long time per byte for a big response — even the Criminal Code (C-46, 5.1MB, about as core an Act as this app will ever be asked for) took 43 seconds to fully download in direct testing, nowhere close to fetchable within any workable request budget. `ai-extract.ts`'s `aiExtractFromUrl` (the shared fetch path behind every URL-based autofill, not just Canada legislation) checks the `Content-Length` header before consuming the body at all — `MAX_FETCH_BYTES` (5MB) — and fails fast with an honest "too large, please upload the PDF or paste details" message instead of buffering the whole thing and eventually hitting the generic, unhelpful timeout fallback. Because the underlying constraint is the source site's own slowness for big responses, not a size this app could realistically raise the ceiling past, a well-known Act like the Criminal Code is expected to need the PDF-upload or paste-text path rather than a pasted URL — this is a genuine limitation of the source, not a bug to chase further.

**Named subscription/login-gated databases** — `BLOCKED_DATABASES` in `lib/autofill/detect.ts` maps a set of domain patterns to a display name; `detectInputType` matches any of them to `'blocked-database'` and `matchBlockedDatabase()` supplies the name so the resulting message ("`{Name}` restricts automated access...") identifies the specific source rather than a generic "couldn't fetch this" note. - `ssrn.com` — the abstract page (`papers.ssrn.com/sol3/papers.cfm?...`) is genuinely Cloudflare-blocked (`cf-mitigated: challenge`); its direct PDF download links (`download.ssrn.com/...`) aren't blocked but are pre-signed S3 URLs that expire minutes after generation (`X-Amz-Expires=300`) — almost always already 404 by the time a student copies and pastes one.

**WA eCourts Portal** (`ecourts.justice.wa.gov.au`) was a real bug, now fixed: every request gets a 302 to a terms-of-use gate, but the 302 response body itself already contains the full decision. `lib/autofill/fetch.ts`'s `fetchWithUserAgentFallback` follows redirects manually and uses a redirect's own body when it's substantial (>2000 chars) rather than silently discarding it — this benefits any similarly-behaved site, not just this one.

**CrossRef-resolved DOIs**: `lib/autofill/crossref.ts` checks CrossRef's own `type` field (`proceedings-article` → Conference Paper fields, not journal fields — this was a real bug, journal was previously hardcoded regardless of actual type). CrossRef doesn't always have conference start/end dates on record (falls back to year-only when absent, per the citation's own stated AGLC4 convention) — if a student needs the exact dates and CrossRef lacks them, the paper's own front matter almost always has them, so PDF-upload or paste-text is the reliable path, not a URL paste.

Two more real bugs found and fixed in the same file:
- **Raw HTML in title/container-title fields.** CrossRef's `title`/`subtitle`/`container-title` come straight from the publisher's XML deposit, not sanitised — confirmed on real records: a Wiley journal name stored as the literal 8 characters `&amp;` (not an actual ampersand), and a Modern Law Review title with a genuinely embedded `<i>Case Name</i>` around an italicised case citation within the article title. `quote()`/`italicize()` (`citation-engine/utils.ts`) are deliberately dumb string wrappers with no HTML awareness, so left alone these rendered as literal `&amp;` text or literal `<i>` tags in the final citation. `cleanCrossRefText()` in `crossref.ts` decodes HTML entities and converts `<i>`/`<em>` tags to this app's own `*text*` italic marker (rather than just stripping them, so the case name keeps its italics) before the text reaches `quote()`/`italicize()` — applied to every text field pulled from CrossRef, not just the ones confirmed broken.
- **Wrong year for online-first articles.** CrossRef's generic `published` field reflects whichever date came first, which for an article published online ahead of its print/volume assignment is the *online* date — not the year the article's own printed citation (and CrossRef's own `published-print`) actually uses. Confirmed on a real record: `published` said 2023, `published-print` and the article's own citation footer both said 2024. `resolveYear()` prefers `published-print` when present, falling back to `published` otherwise.

**PubMed-resolved PMIDs**: `pubmed.ncbi.nlm.nih.gov` article pages themselves are behind a genuine proof-of-work JS challenge (confirmed by direct testing: a SHA-256 leading-zero-bits puzzle served regardless of User-Agent, distinct from a Cloudflare challenge but equally unfetchable) — but `eutils.ncbi.nlm.nih.gov` (NCBI's free public API, a different and unprotected subdomain) returns full structured MEDLINE XML for the same article given its PMID, so this is a real extraction via `lib/autofill/pubmed.ts`, not a "sorry, can't fetch this" fallback. `detectInputType` pulls the PMID straight out of the URL path (`extractPmidFromUrl` in `lib/autofill/detect.ts`, alongside `extractDoiFromUrl` since both are pure URL-parsing helpers kept out of the server-only fetch modules so they stay unit-testable). Older MEDLINE records sometimes have only initials for an author's given name (eg `<ForeName>H A</ForeName>`) rather than a full first name, and MEDLINE always normalises `ArticleTitle` to end with a full stop even when the original didn't have one — `stripTrailingFullStop` (from `citation-engine/utils.ts`) strips that before the citation engine adds its own closing punctuation.

**Treaty extraction had zero system-prompt guidance at all**, unlike every other source type — confirmed as the actual root cause of a real bug report: the UN Treaty Collection's own page (`treaties.un.org/pages/showDetails.aspx`) states a treaty's UNTS registration as a separate `UNTS Volume Number` field in the form `729 (p.161)`, well within the extraction's character budget, but with no instruction on how to read it the model fell back to writing the bare, invalid abbreviation `'UNTS'` with no volume/page at all. Fixed by adding a `treaty` guidance block to `ai-extract.ts`'s `SYSTEM_PROMPT` teaching the `'<volume> (p.<page>)'` → `'<volume> UNTS <page>'` combination, the Australian Treaty Series alternative (`'ATS <number>'`), and — critically — telling the model **not** to invent a UNTS number for a document that doesn't state one: a treaty's own signed text, or a depositary/agency circular reproducing it (eg an IAEA INFCIRC notifying entry into force), is typically issued *before* UN registration assigns a volume/page, so these primary documents legitimately have nothing to extract even though the same treaty does have a UNTS number once registered — `treatySeries` should stay empty rather than fabricated in that case.
  - **This surfaced a real formatting bug in `treaties.ts`, found by testing the genuinely-blank-`treatySeries` case** (a real IAEA INFCIRC PDF of the NPT, which predates the treaty's UN registration): `buildCore()` used to bake a trailing comma directly into each preceding segment (`` `opened for signature ${date},` ``, `` `${titleItalic},` ``) and concatenate the series number and the `(entered into force ...)` clause into one segment, on the assumption something always followed to "absorb" that comma. Whenever a segment actually was empty, the *previous* segment's baked-in comma was left stranded directly in front of whatever came next (eg `'...1968, (entered into force 5 March 1970)'`, or even `'Title, (entered into force ...)'` if the date itself was also missing) — tried gating the comma on "is anything at all following" first, which still failed the same way. The actual fix: the `(entered into force ...)` clause is now built and appended as a plain suffix *outside* the comma-joined `[Title, parties, opened-for-signature/signed date, series]` list, since it never takes a preceding comma regardless of what (if anything) precedes it — it just glues onto whatever the last real content turns out to be.
  - **This also surfaced a real gap in the client-side PDF-upload extraction path**: a treaty's own closing/testimonium clause (`'DONE in triplicate ... the first day of July, one thousand nine hundred and sixty-eight'`) sits at the very end of the document, but `client-extract.ts`'s existing multi-region sampling (page-1 lead + page-2/3 header snippets, tuned for journal offprints) never reached a document's last page at all — so `openedForSignature` came back empty even when the date was genuinely present in the PDF, just unreachable. The server-side PDF-fetch path (`lib/pdf.ts`) already had exactly this kind of trailing sample for Practice Direction/Note signing dates (see below) but it was never ported to the client-side upload path when that feature was built. Fixed by adding a `sampleDocumentEnd()` to `client-extract.ts` that samples the last page's trailing text under the same `[Document end]: ...` label the server-side path and `ai-extract.ts`'s prompt already use, so the existing prompt guidance applies uniformly regardless of which of the two PDF paths a document came in through. Also had to teach the prompt that a treaty's signing date is conventionally spelled out in words, not digits, and must be converted the same as any other date.
  - **Also exposed a genuinely pre-existing bug in `treaties.ts`, unrelated to any of the above**: its bibliography used `ensureFullStop(core)` instead of `stripTrailingFullStop(core)`, contradicting the AGLC4 bibliography convention every other source type follows (no trailing full stop — see `BIBLIOGRAPHY_RULE` in `validator.ts`). Never caught before because `treaties.test.ts` only ever asserted on `footnote`, never `bibliography`. Fixed, and a bibliography assertion added to the existing ICESCR test so it can't silently regress again.
- **A UN General Assembly declaration/resolution (`unDocument`, `un-documents.ts`) is a genuinely different source type from a treaty**, not a variant of one, even though both are frequently hosted on identical-looking instrument-listing pages (OHCHR, un.org, and third-party mirrors of either) — confirmed directly against the UN's own UDHR page, which describes it only as "proclaimed by the United Nations General Assembly ... (General Assembly resolution 217 A)", with no signature/ratification/accession/entry-into-force language anywhere, unlike a genuine treaty. Built by request after the user gave 14 example URLs for "treaties/conventions" and two of them (the Universal Declaration of Human Rights, and the UN Declaration on the Rights of Indigenous Peoples) turned out to be declarations rather than treaties — silently forcing them into `TreatyFields` would have produced a citation with a fabricated or blank UNTS series/entry-into-force date, so a new source type was built instead (user confirmed this was the right call over silently mis-citing them). Format (AGLC4 r 9.2.4): `[Title], GA Res [ResolutionNumber] ([Session]), UN GAOR, UN Doc [Symbol] ([Date][, adopted AdoptedDate]) Pinpoint`. `resolutionNumber`/`session`/`unDocSymbol`/`adoptedDate` are all independently optional and drop out cleanly if the source doesn't state them (a general-audience page routinely gives the resolution number and date but not the formal UN Doc symbol, eg `'A/810'` for the UDHR) — `un-documents.ts`'s `buildCore()` follows the exact same "date-parenthetical-as-plain-suffix, never a comma-joined list item" structure `treaties.ts` uses, for the same reason.
  - **The literal `'UN GAOR'` component and the split `adoptedDate` field were both missed in the initial build** and only surfaced once the user checked the output against real AGLC4 r 9.2.4 citations: the UDHR (`'GA Res 217A (III), UN GAOR, UN Doc A/810 (10 December 1948)'`) needed `'UN GAOR'` inserted, which the first version never produced at all; UNDRIP (`'GA Res 61/295, UN Doc A/RES/61/295 (2 October 2007, adopted 13 September 2007)'`) needed a second, earlier "adopted" date the schema had no field for. `buildCore()` originally inserted `'UN GAOR'` if and only if `session` was populated — inferred from exactly the two worked examples above, since `session` happens to only ever be populated under the older Roman-numeral scheme, and that split happened to line up with whether `'UN GAOR'` belonged in either citation. Flagged in the code at the time as only two data points to generalise from — **and, on later re-reading r 9.2's own element table directly, that inference turned out to be wrong, not just under-confirmed**: 'Official Records' (9.2.4) and 'Session (and Part) Number' (9.2.6) are two distinct rows, not one — the rule itself says elements 9.2.4–9.2.9 (Official Records included) "may be omitted" whenever a document is locatable via its own UN Doc number, entirely independent of which resolution-numbering scheme is in play. Fixed by giving `includeOfficialRecords` its own explicit field on `UNDocumentFields`/`InternationalMaterialFields`, defaulting to unchecked in the UI (`InternationalMaterialForm.tsx`) — the student states it directly rather than it being inferred from an unrelated field; `session` now only ever feeds the resolution-number parenthetical it was always meant to.
  - **The Charter of the United Nations is `unDocument`, cited by bare title alone** — `'Charter of the United Nations.'`, nothing else, no date, no resolution, no UNTS-style series — even though it's the UN's own foundational treaty and pages about it invariably state proper signature/entry-into-force language (San Francisco, 26 June 1945; entered into force 24 October 1945) the same way any other treaty's page would. Confirmed as a genuine special case, not an extraction gap: the app originally classified it as `'treaty'` (a reasonable reading of the content) and rendered the full opened-for-signature/entered-into-force citation, which is exactly what a real treaty gets but not what AGLC4 wants for the Charter specifically. This is unusual enough — and easy enough for a model to override with the truthful, readily-available dates on the page despite being told not to — that prompt guidance alone wasn't trusted: `isUnitedNationsCharter()` in `ai-extract.ts` is a deterministic title check (covering `'Charter of the United Nations'`/`'United Nations Charter'`/`'UN Charter'`) applied at *two* points — once to force `sourceType` to `'unDocument'` even if the model still says `'treaty'`, and again inside `mapFieldsToSourceType`'s `'unDocument'` branch to discard every extracted field except the (canonicalised) title. Same "prompt instruction + deterministic code safety net for an unusual, easy-to-override rule" pattern as `known-treaties.ts`.
  - **`ai-extract.ts` distinguishes treaty from unDocument by content, never by which site hosts the page** — both commonly turn up on near-identical OHCHR/un.org page layouts and share a similar fixed boilerplate line (`'Adopted and opened for signature, ratification and accession by General Assembly resolution 2200A (XXI) of 16 December 1966, entry into force 23 March 1976...'` for a treaty vs `'...proclaimed by the United Nations General Assembly ... (General Assembly resolution 217 A)'` for a declaration) — the presence or absence of signature/ratification/accession/entry-into-force language is the deciding signal, explicitly taught in the prompt alongside how to parse that boilerplate into either shape's fields. The Charter of the United Nations is the one deliberate exception to this test (see above).
  - **OHCHR and the Australian Human Rights Commission (`humanrights.gov.au`) are both genuinely Cloudflare-blocked** (confirmed: `cf-mitigated: challenge` on both, regardless of User-Agent) — every OHCHR instrument-listing URL the user tried failed this way, including the AHRC mirror they specifically asked to be handled even though "this is not the official source." No prompt engineering fixes a network-level block, so both were added to `BLOCKED_DATABASES` in `detect.ts` instead, which now supports a per-entry `defaultSourceType` (new — previously every blocked database silently landed the student on `'researchPaper'`, hardcoded in `lib/autofill/index.ts`; both of these default to `'internationalMaterial'` instead — originally `'treaty'`, updated when Treaty/UN Materials/Foreign Domestic Sources merged into one badge-driven type, see above — since that's the tab covering both of the two source types their content turns out to be, and `matchBlockedDatabaseSourceType()` looks it up). The practical upshot: a treaty/declaration sourced from either site can only be autofilled via PDF upload or paste-text — which is exactly why the treaty/unDocument extraction quality work above matters as much as it does.
- **`lib/autofill/known-treaties.ts`** — a small, hand-verified fallback table of major multilateral treaties' UNTS citations, used only when the source content itself doesn't state one. Confirmed necessary on two separate real PDFs (the ICCPR and ICESCR, both sourced from OHCHR) that a treaty's own plain-text body routinely omits its UNTS registration entirely — the number is assigned separately, during UN registration, and isn't part of the treaty's own text — so no amount of prompt engineering against the *source document* can produce it when it just isn't there. A treaty's UNTS citation is a fixed public fact once the treaty is identified, unlike eg a page number that could plausibly vary, so this isn't the same kind of "invent data that isn't there" the app otherwise studiously avoids (see the treaty/`unDocument` guidance above, and the AU-legislation-pinpoint precedent in "Non-obvious conventions") — but the bar for adding an entry is still high: every citation in the table was checked directly against `treaties.un.org`'s own `showDetails` page or a UNTS volume's own table of contents (not a secondary source) before being added, and one citation found via a secondary source during that process (a law-library guide claiming '189 UNTS 150' for the Refugee Convention) turned out to be wrong — the primary source gives 137. Matches on an exact (case/whitespace-insensitive) title only, via `lookupKnownTreatySeries()`; an unrecognised title returns `undefined` and the field is left blank exactly as before, never a fuzzy/partial match. Wired into `ai-extract.ts`'s `'treaty'` case in `mapFieldsToSourceType`, after the source content's own `treatySeries` extraction.
  - **Extended, by request, with 8 more major treaties outside the human rights set** (Kyoto Protocol, Paris Agreement, UNCLOS, the Rome Statute, VCLT, the Vienna Convention on Diplomatic Relations, UNFCCC, the Montreal Protocol) — same `treaties.un.org showDetails` verification bar, and worth doing again here: the Rome Statute's UNTS citation is very commonly misremembered as '2187 UNTS 90' (that number circulates in some secondary sources) — the primary source gives page 3. Deliberately *not* extended into `known-ohchr-instruments.ts`-style URL-keyed bypass entries for these, since none of their hosting sites (unfccc.int, un.org, icc-cpi.int) have been confirmed Cloudflare-blocked the way ohchr.org is — that only makes sense once a specific host is confirmed unfetchable; until then the existing classification/extraction path should just work for a fetchable page.
  - **`lib/autofill/known-ohchr-instruments.ts` takes this one step further, by request**: for a fixed, explicitly-requested set of 13 major OHCHR instrument URLs (12 treaties plus UNDRIP, a `unDocument`), the *entire* citation — title, opened-for-signature date, series, entered-into-force date, or for UNDRIP the resolution number, UN Doc symbol, document date, and separate adopted date — is supplied directly, keyed by the instrument's own URL path, bypassing the fetch (and the AI extraction call) entirely. This only exists because ohchr.org is a genuine, unfixable Cloudflare block (see below) — every one of these 13 URLs would otherwise dead-end at the generic "OHCHR restricts automated access" message with an empty form, even though the specific instrument is perfectly identifiable from the URL alone and its citation is a fixed public fact. `detectInputType()` checks this (via `matchKnownOHCHRInstrument()`) *before* the generic `blocked-database` check, so only these 13 exact URLs short-circuit — every other ohchr.org page still correctly falls through to the ordinary "please upload a PDF" message. Ships `confidence: 'high'` and an explicit message telling the student this data came from Pinpoint's own reference table rather than a live fetch, so it's never mistaken for a real extraction. Every date/series was verified the same way as `known-treaties.ts` (against `treaties.un.org`'s own pages, or the ILO/OHCHR's own stated adoption text where the UN registration page wasn't separately checked) before being hardcoded.
- **`docs.un.org/en/{ResolutionSymbol}` pages (`lib/autofill/docs-un-org.ts`) never carry any real content to fetch at all — a genuinely different failure mode from ohchr.org's Cloudflare block, needing a genuinely different fix.** The page itself is just a thin "Document Viewer" shell that loads the actual resolution/instrument PDF client-side into an `<iframe>` pointing at a *different* domain (`documents.un.org`) — a plain server-side HTML fetch (cheerio, no JS execution) sees only the shell, never the real content, regardless of extraction-prompt quality. But the iframe's own `src` — `https://documents.un.org/api/symbol/access?s=<symbol>&l=en&t=pdf` — is a plain, unauthenticated API that round-trips through two redirects straight to the real PDF with no blocking whatsoever (confirmed by direct testing). `rewriteDocsUnOrgUrl()` rewrites the URL *before* the fetch in `aiExtractFromUrl()`; the existing generic PDF-content-type handling there (already used for any URL that happens to resolve to a PDF) takes it from there unmodified — no new extraction pathway needed, no per-document hardcoding, since the rewrite is purely mechanical (any resolution symbol, not a fixed list). Requested by the user after they linked `research.un.org`'s "Conventions & Selected Declarations Adopted by General Assembly Resolutions" table — a list of 150+ resolution symbols going back to 1946 — as a way to check the URLs it links to actually work; this one fix generalises to the whole table (and to any other `docs.un.org` URL) rather than needing per-row verification.
  - **Confirmed live that the existing content-based treaty/unDocument classifier (see above) generalises correctly across this table without further changes**, including a case worth knowing about: the same resolution can serve *either* role depending on what its own text actually says, not on what kind of instrument it is in the abstract. The Optional Protocol to CAT (A/RES/57/199) — itself a separately-ratified treaty — classified `treaty`, since its resolution text states a concrete "opened for signature" date. The UN Convention against Cybercrime (A/RES/79/243, adopted December 2024) classified `unDocument` instead, because *that* resolution's text is prospective ("requests the Secretary-General to open the Convention for signature") rather than stating a date signature actually began — a defensible, content-driven distinction rather than a misclassification, but worth being aware of for a very recently adopted convention that hasn't yet been opened for signature at the time a student cites it: re-checking after signature has actually opened (or citing the treaty's own later, separately-published text once available) may give a more complete `treaty`-style citation.

- **`AutofillBar.tsx` — all three autofill input methods (URL/DOI, PDF upload, paste citation details) are always visible and independently usable at once**, requested by the user after the original design gated the latter two behind "upload a PDF"/"paste citation details" toggle buttons a student had to click to even see. `showPasteText` (the old toggle's boolean state) is gone entirely, and each `run*` function clears the *other two* inputs on submit (not just its own), so a stale value doesn't linger visually in a box that wasn't the one just used.

- **Two further speed levers were attempted on top of the caching fix above, at the user's explicit request, and both had to be abandoned after live testing uncovered a serious, undocumented Anthropic structured-output limitation — recorded here in detail specifically so this isn't attempted again without knowing it's already been tried.** The request was "speed up retrieval while keeping token cost down"; the two levers were (1) making `ExtractionSchema`'s ~40 always-required fields `.optional()` so the model could omit whichever ones don't apply to a given extraction instead of writing them out as `""`, cutting output tokens (and so both cost and generation time) on every call, and (2) streaming the autofill response so the citation form fills in field-by-field as the model's JSON arrives instead of the UI sitting blank for the ~10s a full extraction takes.
  - **The critical discovery: adding `.optional()` to *any* meaningful subset of `ExtractionSchema`'s fields makes every extraction call hang indefinitely — 30+ seconds, no response, no error — regardless of whether the call is streamed or not.** This is a *different* failure mode from the already-known, already-documented "compiled grammar is too large" error (which fires immediately, with a clear message, when the schema has too many *fields* overall) and from a second, newly-discovered one hit along the way — a 400 "Schemas contains too many optional parameters (N)... limit: 24" when *all* ~47 non-enum fields were marked optional at once (fails fast, with a clear message, easy to react to). The hang is worse than either: it doesn't fail, it just never completes, even for a deliberately small, carefully-chosen subset of 20 optional fields — comfortably under the documented 24-optional-parameter ceiling, and confirmed live via `usage` on the request that DID complete (structured output was in fact correctly generated once forced through non-streaming — see below) that the schema itself wasn't rejected. Confirmed the hang is real and reproducible, not a fluke or an artifact of this app's own code, via four separate direct API calls made completely outside Next.js (plain Node scripts against the real Anthropic API): (a) the full schema (47 optional) via `.stream()` — hung; (b) the reduced schema (20 optional) via `.stream()` — hung; (c) the *same* 20-optional schema via non-streaming `.parse()` — also hung, ruling out streaming itself as the cause; (d) the exact same system prompt and content with the schema's fields reverted to *zero* optional (its original, all-required shape) via `.parse()` — completed reliably in ~10s, every time. A fifth test — the full 20-optional schema via `.stream()` but with `output_config.format` removed entirely (plain prompted JSON, no structured-output constraint) — also completed fast (~4s), confirming the hang is specific to *constrained-decoding grammar compilation* for a schema this size once any field becomes optional, not to system-prompt size, output length, or streaming in general. A middle-ground test (a hand-trimmed 13-field schema, structured-output constraint intact, via `.stream()`) worked fine and fast (~10s) — so the trigger is specifically "large overall schema (11 source types' worth of fields sharing one object) + any optional fields", not "optional fields" or "large schema" independently; either alone is fine, the combination isn't.
  - **Given this, both levers were fully reverted** — `ExtractionSchema` is back to every field required (its original, months-tested-working shape) with the "always empty string, never omitted" prompt instruction restored to match; `runExtraction`/`aiExtractFromUrl` are back to a single non-streaming `.parse()` call, and `autofillStreaming` (`lib/autofill/index.ts`), the NDJSON streaming shape of `POST /api/autofill` (`route.ts`), and the `onAutofillProgress` prop threading through `AutofillBar.tsx`/`Generator.tsx` were all removed rather than left in place unused — there was no safe subset of the schema this session found that streams (or even non-streams) reliably, so there was nothing left for that plumbing to usefully carry. Confirmed via `tsc`/`lint`/`vitest` (485 tests) and a full rebuild that the revert is clean, and via two live end-to-end calls (through the running app, not a standalone script) — the Migration Act and Privacy Amendment (Office of the Privacy Commissioner) Act, both `high` confidence, correct fields, ~9-12s — that the app is back to exactly the reliable state the caching fix alone produced.
  - **If revisiting either lever**: the schema most likely needs to be split into several smaller per-source-type (or per-related-category, eg "Foreign Domestic Sources' Canada/US fields" as their own schema) structured-output calls rather than one shared ~48-field object covering all 11 source types at once — the 13-field success case suggests a schema in something like that size range is safely within whatever limit is actually being hit, well under the ~24-27 field range that hangs. That's a materially bigger, riskier change than either lever attempted here (it touches the model's own source-type classification step, which currently happens *inside* the single shared call) and deserves its own scoped design pass and the user's sign-off before starting, not a quick follow-on. Streaming specifically would also need a real partial-JSON incremental parser (a regex-based one was built and worked correctly against real streamed text in this session's testing, before the schema hang made it moot) and a decision about the "no `output_config.format`, prompted-JSON-only" fallback's reliability trade-off (confirmed fast, but confirmed *not* schema-enforced — the model visibly deviated from the intended shape in that exact test) if constrained decoding turns out not to be salvageable for a schema large enough to be useful.

Live-verified end-to-end through the browser: instant response, correct message naming "La Trobe University", correct tab. `tsc`/`lint`/`vitest` (485 tests) and a full rebuild all confirmed clean. If another `latrobe.edu.au` page (or a different university/organisation site) is reported as failing to autofill, check for this exact signature first (`curl -sD - <url> | grep -i cf-mitigated`) before assuming it's an extraction-quality problem — a genuine Cloudflare/WAF block and a bad extraction look identical to a student (autofill just doesn't work) but need completely different fixes, and this list is exactly where the former belongs.

- **Immediately generalised beyond `latrobe.edu.au`, at the user's own follow-up request ("can this be done for any URL that is Cloudflare protected?") — `ai-extract.ts` now detects a genuine Cloudflare block at fetch time for *any* domain, not just ones pre-registered by name.** New `isCloudflareChallenge(response: Response): boolean` in `fetch.ts`: primarily checks `response.headers.get('cf-mitigated') === 'challenge'` — Cloudflare's own diagnostic header, and the confirmed, consistent signal behind every single Cloudflare-block entry manually added to `BLOCKED_DATABASES` so far (SSRN, AustLII, NSW/SA legislation, APO, OHCHR, Congress.gov, Merriam-Webster, La Trobe); falls back to a plain `403` branded `server: cloudflare` when that header's absent, for the rarer case a challenge response doesn't carry it. Wired into `aiExtractFromUrl`'s existing fetch call: right after the fetch (before the generic `!response.ok` throw that used to lead to a vague "Could not extract details" message regardless of cause), a detected challenge short-circuits straight to a new `cloudflareBlockedResult(url)` — same shape and wording as the curated `BLOCKED_DATABASES` message, just using the URL's own hostname (`www.` stripped) in place of a hand-curated display name, since there's no pre-known one for a domain nobody's registered yet. `BLOCKED_DATABASES` still matters and wasn't replaced — it skips the fetch attempt entirely (instant, not even a network round-trip) for a domain already *known* to always fail this way, and gives a properly curated name/`defaultSourceType` a bare hostname can't — but every domain not yet in that list now gets this same honest, actionable message the very first time it's tried, instead of only after being individually reported, tested, and added by hand.
  - **The secondary (no-`cf-mitigated`-header) heuristic has a real, confirmed precision limit, and the message wording was deliberately built around it rather than ignoring it.** Tested live against `researchgate.net` (not in `BLOCKED_DATABASES`) specifically to probe this: `403`, `server: cloudflare`, but *no* `cf-mitigated` header — and the response body turned out to be ResearchGate's own `"Temporarily Unavailable"` block page, not a Cloudflare-issued challenge at all; Cloudflare there is just the CDN the origin happens to sit behind, the same as a huge fraction of the modern web. The *practical* outcome for a student is identical either way (this URL genuinely can't be fetched, manual/PDF entry is genuinely the right next step) so the secondary heuristic is still worth keeping — but `cloudflareBlockedResult()`'s message deliberately never names "Cloudflare" specifically (matching how every existing `BLOCKED_DATABASES` entry's shared message template already doesn't either), only "restricts automated access", so it stays accurate regardless of which of the two signals actually fired.
  - **Live-verified against two more real, previously-unregistered domains** — `onlinelibrary.wiley.com` (a non-DOI-shaped URL, to reach this path rather than the pre-existing embedded-DOI-to-CrossRef shortcut most Wiley URLs take instead; genuine `cf-mitigated: challenge`) and `researchgate.net` (the no-header secondary-heuristic case above) — both returned instantly (sub-2s, not the ~20-30s a real failed-fetch-then-generic-fallback attempt used to take) with the correct hostname-derived message, through both a direct API call and the full browser UI. `tsc`/`lint`/`vitest` (485 tests) and a full rebuild all confirmed clean.
  - **Deliberately scoped to `aiExtractFromUrl` only, not retrofitted into every other fetch-based handler in this file/directory** (`au-legislation.ts`, `austlii-cases.ts`, `canada-legislation.ts`, etc.) — this is the single highest-leverage location since it's the generic catch-all path nearly every URL not claimed by a more specific deterministic handler eventually funnels through (including, confirmed by re-reading `au-legislation.ts`, every AU state/territory jurisdiction *not* already in its own separate `KNOWN_BLOCKED_DOMAINS` set, via its own "no sourceType hint" call into this same function) — so this one change already covers the dominant case without needing to touch a dozen other files' worth of independent fetch/error-handling logic that, as far as this session knows, isn't currently misbehaving.

- **Two new deterministic, non-AI citation warnings, requested by the user in one go: (1) a note when a core AGLC4 element is missing from the fields themselves (their own example: legislation autofilled with no year), explicitly never covering pinpoints; (2) a fixed reminder on any unreported case that AGLC4 prefers a reported version where one exists.** New `lib/citation-engine/warnings.ts`, exporting `getMissingFieldsWarning(sourceType, fields)` and `getUnreportedCaseWarning(sourceType, fields)`, both called once from `generateCitationSync` itself (`index.ts`) and merged into a new `CitationResult.warnings?: string[]` array — deliberately computed in the *synchronous*, deterministic rules engine, not the AI validator, so a warning is never contingent on that call succeeding, being fast, or even being reachable (see the caching/latency work earlier in this file), and is available the instant a citation is generated, in both the sync preview `Generator.tsx` uses for live typing and the async AI-checked result. Rendered in a new `WarningNotes` component in `CitationOutput.tsx` — full-sentence amber notes (the same amber already used for a low-confidence validation pass) rather than squeezed into the pill-shaped badge row, since these are sentences a student needs to actually read, not one-word states; shown regardless of whether AI validation has finished, since they don't depend on it.
  - **One checker function per source type** (mirroring `generateCitationSync`'s own per-type dispatch shape exactly, branching further by subtype/report-type/book-type wherever a source type has one), built directly off each `*Fields` interface in `types.ts` — which turned out to already document, field by field, which are genuinely core vs "frequently and legitimately absent" (see eg `ReportFields`'s own comment on why authors are so often omitted, or `validator.ts`'s hand-verified guidance on treaty/UN-document fields, reused here rather than re-litigated). Two real edge cases found and fixed by cross-checking against the *formatters* (not just the field types) before shipping, both confirmed live:
    - **`LegislationFields.year` is required everywhere except the bare Commonwealth Constitution** (`jurisdiction === 'none'`, per `LegislationForm.tsx`'s own dropdown label and AGLC4 r 3.6) — checked directly against `legislation.ts`'s formatter, which already handles a blank year there gracefully; the missing-fields checker now skips the year check for that one case instead of falsely flagging it. Same reasoning already applied correctly to `constitutionYear` in `otherLegislativeMaterialFields`'s own `'constitution'` subtype from the start (that field was never checked).
    - **The Charter of the United Nations is cited by bare title alone (r 9.2.4)** — every other UN Materials field, `date` included, is correctly blank for it. The detection for this (`isUnitedNationsCharter`/`UN_CHARTER_TITLES`) used to live as a private copy inside `ai-extract.ts` (`'server-only'`, so unreachable from the plain citation-engine layer `warnings.ts` needs to run in, including client-side) — moved to `lib/citation-engine/utils.ts` (already a plain, portable file every formatter imports from) and exported, so `ai-extract.ts` and `warnings.ts` now share one definition instead of risking two silently drifting apart; `ai-extract.ts` updated to import it from there instead of keeping its own copy.
    - **`CaseFields`'s unreported-no-mnc branch is the one place Judge is core, not optional** — confirmed directly against `CaseForm.tsx`'s own JSX, which (unlike the `reported` and `unreported-mnc` branches) doesn't mark Judge `optional` there, matching AGLC4 r 2.3.2's own '(Court, Judge(s), Full Date)' form exactly.

Left as an explicit, commented scope decision in `warnings.ts` rather than a silent gap, and mentioned to the user as a known limitation rather than claimed as complete.
  - **24 new tests in `warnings.test.ts`**, covering: every source type's missing-field detection, both `LegislationFields`/`OtherLegislativeMaterialFields` Constitution no-year exceptions, the UN Charter no-date exception, the Judge-is-core-only-for-unreported-no-mnc case, that a pinpoint is never flagged, dictionary/legal-encyclopedia's "exactly one of two modes" (hard copy vs online) logic, and that `foreignDomestic`/`europeanUnion` correctly return nothing. `tsc`/`lint`/`vitest` (509 tests, up from 485) and a full rebuild all confirmed clean; live-verified through the actual browser with the user's own worked example (legislation, blank year) and both unreported case-type branches, including confirming both warnings can render at once and that they clear the instant the fields are actually complete.

## PDF upload internals — bugs to know about if you touch this

1. **`'use client'` does not stop server-side evaluation.** `pdfjs-dist` references browser-only globals (`DOMMatrix`) at module-load time, which crashes if evaluated in Node — and Next.js *does* evaluate client-component modules in Node during the initial SSR pass, `'use client'` notwithstanding (it only marks the RSC boundary). Fixed by deferring `pdfjs-dist` behind a dynamic `import()` inside `extractPDFMetadata()` rather than a static top-level import — this also halved the page's JS bundle, since the library is now lazily code-split.
2. **The worker file can't be resolved via `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url)`** — Next's production build runs Terser over anything pulled in that way, and Terser chokes on the worker bundle's `import.meta` syntax. Fixed by copying the worker into `/public` via a `postinstall` script and referencing it as a plain static path (`/pdf.worker.min.mjs`) instead, which sidesteps webpack/Terser entirely.
3. **A DOI buried past the text budget beats AI-parsing a citation footer.** Most journal-article PDFs (Cambridge, Springer, Elsevier, Wiley, ...) print the article's own DOI somewhere on page 1, usually in a footer alongside the full published volume/issue/page — eg `European Journal of Risk Regulation (2024), 15, 431–446 doi:10.1017/err.2023.57`. Confirmed on a real PDF where that footer sat at character ~3045 of a 3178-character page 1, well past `client-extract.ts`'s ~2000-character leading-text budget, so the volume/issue/page never reached the server at all. `findCitationBlock()` in `client-extract.ts` now also matches a bare `doi:`/`doi.org/` pattern (not just labelled "Cite as:"-style blocks) and captures a window *around* it, since the DOI is typically the tail of its citation footer with the journal/volume/page text immediately before it. Once that text reaches the server, `extractViaEmbeddedDoi()` in `ai-extract.ts` looks any DOI it finds up directly against CrossRef *before* attempting the generic AI-text extraction — the same authoritative pipeline a pasted DOI or DOI URL already gets, and far more reliable than teaching the model every publisher's footer shape.

## CCH pilcrow stripping, instant warning-clearing, autofill-bar wording, and large-PDF handling

Four independent fixes/features from the same round, covered together since two of them (the pilcrow stripping and the large-PDF handling) each turned out to have a second layer once the first fix was live-tested.

- **`stripPilcrow` (`citation-engine/utils.ts`) removes CCH iKnowConnect's `'¶'` paragraph marker** (eg `'Aust Torts Reports ¶83-437'`, pasted verbatim from CCH's report-series pinpoint) — a house style of that publisher's, not part of the AGLC4 citation itself. Applied in two places, both necessary:
  - **`cases.ts`'s `formatReported()`** strips it from `startingPage` directly (`stripPilcrow(fields.startingPage)`), and **`pinpointValue()`** (the shared helper every formatter's `formatPinpoint()` ultimately calls) strips it from any in-text pinpoint too — a paragraph-type pinpoint copied with its own leading `'¶'` would otherwise have rendered as `[¶83-440]` (a doubled marker), not the correct `[83-440]`. This covers every source type that uses a pinpoint, not just cases.
  - **A second, separate leak was found only by live-testing the user's own CCH example end-to-end**: even with `startingPage` correctly stripped in the *unvalidated* base citation, the AI validator (`validateCitation` in `validator.ts`) still reintroduced the pilcrow into its `correctedFootnote`. Root cause: the validator's prompt sends the **raw source fields** as JSON context (`Source fields used to generate them: ${JSON.stringify(fields)}`) alongside the already-generated footnote/subsequent/bibliography strings, so the AI can reason about the underlying data — but when it decides to correct *anything* (in this case, an unrelated bracket-type check), it reconstructs the whole footnote from that raw JSON, which still had the unstripped `'¶83-437'`. Confirmed live: the sync-generated citation was already clean, but the badge showed "Corrected" and the pilcrow was back. Fixed with `sanitizeFieldsForValidation()` (`citation-engine/utils.ts`, not `validator.ts` — deliberately kept in the plain, non-`'server-only'` file so it's unit-testable without mocking the Anthropic SDK), which strips every string/string-array field the same way before they're ever serialised for the AI. This closes the gap for *any* future normalisation this app applies, not just this one character — a lesson worth remembering any time a new deterministic string transform is added to a formatter: check whether the validator's raw-field JSON context needs the same treatment, since the AI can always reconstruct output straight from that JSON regardless of what the formatter already cleaned up.
- **Warning notes (`warnings.ts`'s missing-fields/unreported-case reminders, rendered by `CitationOutput.tsx`'s `WarningNotes`) now clear the instant a new autofill attempt starts, not when it finishes.** Previously they were driven purely by `result.warnings`, which only changes once the fields-watching `useEffect` in `Generator.tsx` recomputes a citation — meaning a stale warning from the *previous* citation stayed on screen through the entire loading/fetching phase of a new one, which could be several seconds for a slow fetch. Fixed with a small `useEffect` in `Generator.tsx` watching `autofillLoading` (already wired from `AutofillBar`'s `onLoadingChange`, itself already firing the instant `status` flips to `'loading'` at the very start of `runAutofill`/`runPasteText`/`runUpload` — no new plumbing needed, just a missing consumer of state that already existed): the moment loading starts, `setResult` strips `.warnings` from whatever result is currently showing, leaving everything else (the actual citation text, the source-type panel) untouched so the screen doesn't go blank mid-fetch — only the stale warning disappears immediately. Confirmed live: pasting a case with a "Missing Volume" warning, then immediately pasting a different, complete citation — the warning vanished the instant "Extracting details…" appeared, well before the new citation resolved.
- **The autofill bar's URL placeholder no longer singles out AustLII.** Was `'Paste a URL, DOI, or AustLII link…'`, which reads as if AustLII were a distinct third kind of input rather than just one of many supported URL sources (legislation.gov.au, CrossRef DOIs, government report sites, etc.) — changed to `'Paste a URL or DOI…'`. The second, paste-details textarea's own placeholder (`'Or paste the case name, citation, author, title…'`) already covers the non-URL case and wasn't touched.
- **Large PDFs (eg a 16MB+ government annual report) are now fetched and parsed directly instead of being rejected outright**, following a live investigation of the user's own example (`homeaffairs.gov.au`'s 2023-24 annual report, 16.2MB). Two changes, addressing the two genuinely separate costs a huge PDF imposes:
  - **`MAX_FETCH_BYTES` (`ai-extract.ts`) raised from 5MB to 25MB.** The original 5MB threshold conflated file *size* with fetch *risk*, but direct testing showed size alone isn't the risk — speed is: the 16.2MB homeaffairs.gov.au PDF downloads in well under 2 seconds (confirmed via `curl`, static file, `accept-ranges: bytes`), while a *much smaller* file on a slow host (laws-lois.justice.gc.ca's Criminal Code, 5.1MB, 43 seconds in earlier testing — see the existing comment on this constant) is the actual danger. The threshold is raised generously rather than removed entirely, since a truly pathological document (hundreds of MB, or a large file on a slow host) is still caught by the existing `FETCH_TIMEOUT_MS` abort regardless of this check, degrading gracefully to the ordinary `fallbackResult()` message rather than hanging.
  - **`extractPdfText()` (`lib/pdf.ts`) skips the body of a long PDF instead of laying out and extracting text from every single page.** A citation's own details (title, issuing agency, date) are overwhelmingly on the cover page or in the front matter — a 200+ page annual report never needs its body read to be cited, and unpdf's `mergePages` extraction walking every page is the dominant cost for a genuinely huge PDF, well beyond the network download itself. Past `LARGE_PDF_PAGE_THRESHOLD` (30 pages), it now reads only the first `LARGE_PDF_LEADING_PAGES` (12) plus the last `LARGE_PDF_TRAILING_PAGES` (3) — the trailing slice exists for the same reason `TRAILING_SAMPLE_LENGTH`'s character-level trailing sample already does (a signed report/Act/treaty can place its issuing date in a closing signature block) — using pdf.js's own per-page `getTextContent()` API directly (`pageText()`/`pageRangeText()`, mirroring unpdf's own internal per-page join logic exactly, since unpdf doesn't expose a page-range option through its `extractText()` wrapper). This is the literal implementation of "read just the first few pages" the user asked about — but at the *parsing* layer, not as an HTTP Range request: a naive byte-range fetch of only a PDF's first N bytes was investigated and rejected, since a non-linearized PDF (the overwhelming majority of real-world government/report PDFs) keeps its structural xref/trailer table at the very *end* of the file — a byte-truncated download is missing that entirely and fails to parse as a PDF at all, regardless of the server supporting Range requests. Reading the full (now permitted, and fast-to-download) buffer but only asking pdf.js to lay out a handful of pages sidesteps that constraint entirely while still delivering the actual speedup.
  - **Confirmed live, end-to-end**: the homeaffairs.gov.au URL, which previously hit the hard "too large" rejection, now returns full high-confidence extraction — `Department of Home Affairs, Annual Report 2023–24 (Report, 2024)` (documentType genericised per the r 7.1.1 fix below), correctly classified as `'report'` — rather than merely a better-guessed source type.
  - **A URL-only source-type guess was still added as a fallback for the genuinely-too-large/too-slow case** (`guessSourceTypeFromUrl()` in `ai-extract.ts`, used by both `tooLargeResult()` and `fallbackResult()`), since some document will always exceed even the raised threshold, or time out on a slow host — that path previously always defaulted to `'website'` even for an obvious report (the user's own example: `.../reports-and-pubs/Annualreports/home-affairs-annual-report-2023-24.pdf` hits both `'reports-and-pubs'` and `'annual-report'`). Deliberately narrow — matches only unambiguous report-type path/filename signals (`reports-and-pubs`, `annual-report`, `annualreport`, `discussion-paper`, `white-paper`, `policy-document`) and falls through to the existing `'website'` default otherwise, rather than a broad classifier guessing from thin evidence — same "no guess is safer than a confidently wrong one" bias already established for the `internationalMaterial` warnings scoping (see `warnings.ts` above).

## r 7.1.1 generic document type, slow-operation notice, and the conference-paper date reminder

Three more from the round after the one above.

- **AGLC4 r 7.1.1's "generic document type" rule now has a deterministic backstop** (`genericiseIntegralDocumentType()` in `lib/autofill/utils.ts`, applied in `mapFieldsToSourceType`'s `'report'` case so it covers all three autofill paths — URL, PDF upload, paste text). The rule: where a document-type label forms an *integral* part of the title (the title is essentially just that label plus a year/edition, with no distinct name or tagline of its own), the label stays in the title and the *generic* document type goes in the parentheses — a document titled 'Annual Report 2023–24' is cited `... Annual Report 2023–24 (Report, 2024)`, never `(Annual Report, 2024)`. The `ai-extract.ts` system prompt has stated this rule (with this exact worked example) for a while, but the model doesn't reliably apply it — confirmed on the Home Affairs 2023–24 annual report, which came back `(Annual Report, 2024)`. The backstop is scoped to the `'...Report'` family only — the one document-type family whose integral form differs from its own generic; `'White Paper'` and `'Policy Document'` are already their own generic forms under the same rule, no collapse needed — and only fires when what's left of the title after removing the label and any year/number tokens is empty, so a genuine descriptive title that merely contains the words (eg `'Interim Report on the Operation of the Foo Act'`) keeps whatever split the model chose. Confirmed live: the Home Affairs URL now renders `(Report, 2024)`.
- **The autofill bar shows a "still working" notice after 4 seconds** (`SLOW_NOTICE_MS`/`SLOW_NOTICE_TEXT` in `AutofillBar.tsx`, wired into both `runUpload` and `runAutofill` via `startSlowNotice()`/`clearSlowNotice()`). A PDF — uploaded, or fetched from a URL that turns out to be one — can be hundreds of pages, long enough that even the trimmed parse (see `LARGE_PDF_PAGE_THRESHOLD` above) runs well past a second or two; a bare unchanging "Extracting details…" for 10+ seconds reads as a hang. The notice renders as a second grey line under the existing loading message rather than replacing it, so the normal `Reading page… → Extracting details…` progression is untouched. Confirmed live: appeared mid-fetch on the 16MB Home Affairs PDF.
- **A conference paper whose autofilled date is year-only now carries an AGLC4 r 7.2 reminder** (`getConferencePaperDateWarning()` in `warnings.ts`, wired into `generateCitationSync`'s `warnings` array alongside the existing two checks). r 7.2 cites a conference/proceedings paper with the *full* date of the conference (eg '3–10 March 2021'), not just the year — but autofill frequently can't recover it: confirmed by direct API inspection that CrossRef's `event` metadata for the ACM FAccT '21 proceedings (`10.1145/3442188.3445922`, the user's own example) carries only the conference name, acronym, location and sponsor — no `start`/`end` date-parts — and `dl.acm.org` itself is Cloudflare-challenge-blocked (`cf-mitigated: challenge`), so there's no second source to fall back to. `formatConferenceDate()` in `crossref.ts` already degrades correctly to the bare year in this case; deliberately *not* substituting the `published-print` date (a single publication date, `3 March 2021` here) since that's not the conference date range and would be a confidently-wrong value. The warning fires only for a year-only date (`/^\s*\d{4}\s*$/`) on a `documentType` matching `/conference|proceedings/i` — not for a blank date (already covered by the missing-fields check), not once a full date is present, and not for a thesis/working paper where a year-only date is normal. So the answer to "is this because the engine can't retrieve the dates?" is yes — and now the citation says so and tells the student to add them.

## Institutional-author bibliography fix, and large-PDF / AustLII prod-hardening

Came out of an architecture review — one thing the engine leaned on the AI validator for that it shouldn't, and two deterministic paths that work in dev but are exposed in production.

- **`formatBibliographyAuthorList` no longer inverts an institutional first author** (`isInstitutionalAuthor()` in `lib/citation-engine/utils.ts`). `invertName` blindly splits on the last space to make "Surname, Given" — for a body ("Department of Home Affairs", "Australian Law Reform Commission", "Cisco") that produced "Affairs, Department of Home", wrong under AGLC4 r 4.1 (institutional authors are listed in natural order, never inverted). This is used by report, journal, research-paper, website, newspaper and book bibliographies. Until now the *only* thing catching it was the AI validator — confirmed live: the Home Affairs annual-report citation used to come back "Corrected · high confidence" with the validator flipping the name; it now comes back "AGLC4 check passed ✓" because the deterministic engine gets it right first. `reports.ts` already relied on this exact insight for its *subsequent* references ("a body has no 'surname' to extract… 'Woolworths Group' would give the nonsensical 'Group'") — this just brings the bibliography into line. `isInstitutionalAuthor` is deliberately conservative (a false positive leaves a real person's name un-inverted, also an error): a single-token name, or one containing a marker word that essentially never appears in a personal name (department/commission/bureau/authority/university/institute/foundation/council/corporation/pty/ltd/plc/… — full list in the file). Same shape as `isUnitedNationsCharter` and the report-series maps.
- **Large-PDF fetch, production hardening** (`ai-extract.ts`, plus `maxDuration` on the three `/api/autofill*` routes). The earlier `MAX_FETCH_BYTES = 25MB` change is correct in local dev (fast disk, no platform limits) but exposed in a serverless deploy. Four mitigations:
  - **`export const maxDuration` on `app/api/autofill/route.ts` (45), `app/api/autofill/pdf/route.ts` (45), `app/api/autofill-text/route.ts` (30).** Each route already self-caps via `Promise.race` against a `REQUEST_TIMEOUT_MS`, but Vercel's *default* function limit is 10s on Hobby — well under those caps — so without this the platform would kill a slow large-PDF fetch before the graceful `timeoutResult()` could return. `maxDuration` just raises the platform ceiling above the internal cap.
  - **Separate `MAX_PDF_FETCH_BYTES = 18MB`, distinct from HTML's `MAX_FETCH_BYTES = 25MB`.** Once fetched, a huge HTML page is one `cheerio.load` from usable, but a large PDF then has to be structurally parsed by pdfjs on a constrained serverless CPU on top of the download. 18MB still clears a real government annual report (the homeaffairs.gov.au case, 16.2MB, verified still working) with headroom, but stays below where a 25MB parse would be gambling against `REQUEST_TIMEOUT_MS` in prod.
  - **`readBodyWithLimit()` — an actual streamed byte counter**, replacing a bare `response.arrayBuffer()` / `response.text()`. The old Content-Length precheck (kept as a fast path) misses any server using chunked transfer encoding, which omits that header entirely — the code even acknowledged this. Now the body is read chunk-by-chunk and aborted the moment it crosses the cap, bounding memory and time regardless of what headers the server sent. The HTML path decodes the streamed bytes via `decodeHtmlBody()` (honours a `charset=` in the Content-Type, falls back to UTF-8) to stay equivalent to what `response.text()` did — verified live on a normal OAIC page, no regression.
  - **A fetch aborted by `FETCH_TIMEOUT_MS` now returns `tooLargeResult()`**, not the generic `fallbackResult()`. "Too slow to pull down in time" is, for the student, the same "get it another way" situation as "too large" — so it gets the same actionable "upload the PDF / paste details" message rather than one that reads as if Pinpoint's parsing broke. `tooLargeResult()`'s wording was broadened to "too large or slow" to match.
- **AustLII case-citation parsing rewritten to be anchored and validated** (`lib/autofill/austlii-cases-parse.ts`, new; `austlii-cases.ts` now just fetches + hands off). The old `REPORTED_CITATION_PATTERN` was run with `.match()` against the *entire page body*, first hit wins — effectively "first `<number> <Capitalised words> <number>` anywhere on the page". It worked only because AustLII pages happen to lead with the citation; any markup change putting something else first (a nav label, a docket line, an in-text "12 Corporations Act 2001" reference) would yield a confident wrong volume/abbreviation/page at `confidence: 'high'` — and unlike the rest of that file, which fails cleanly to `fallbackResult()`, a false regex match produces authoritative-looking bad data. Three changes: (1) the patterns now see only the page `<title>` plus the first 500 chars of body text, not the whole thing; (2) the abbreviation sub-pattern is bounded to 1–4 short words instead of an unbounded `[A-Za-z\s]+`, and a match is run through `isPlausibleReportedCitation()` (sane volume/page ranges, abbreviation length/word count) before it's trusted at all; (3) `confidence` is `'high'` only when the abbreviation is in `report-series.ts`'s known set (new `isKnownReportSeries()` export) — a plausible but unrecognised series drops to `'medium'`. Can't be end-to-end verified live (AustLII is Cloudflare-blocked), but the pure parser has its own `*-parse.test.ts` including an explicit "don't false-match body text far down the page" regression test.

## CrossRef bibliographic (title) match on the paste-text path

For pasted text that names a journal or conference paper but carries no DOI and no URL — a title + authors off a reading list, say. CrossRef metadata is authoritative where the free-text model parse is only as good as what the student typed, so `aiExtractFromPastedText` now tries, in order: an exact CrossRef lookup on any DOI embedded in the text (`extractViaEmbeddedDoi`, previously only wired into the PDF path), then a **gated** CrossRef title search, then — only if neither produced a match — the existing model parse. Same "authoritative source beats AI parsing" instinct `extractViaEmbeddedDoi` already embodies, one step earlier.

- **`fetchCrossRefByBibliographic()` (`crossref.ts`)** queries `api.crossref.org/works?query.bibliographic=<pasted text, ≤300 chars>&rows=5`, requesting `event` in the `select` so a conference paper gets the same clean institution name (`buildInstitutionName` → "Association for Computing Machinery Conference on…") the DOI path produces, not the raw `container-title`. Result is capped at `confidence: 'medium'` — never `'high'`, since this is a fuzzy match, not a lookup by identifier — and carries a `message` + `verifyUrl` shown in `Generator`'s notice banner (see the two bullets below for the current wording and placement). Negative results aren't cached; a hit is.
- **The acceptance gate is deterministic and strict — a silently-wrong "closest work" is the one outcome that makes this feature net-negative** — and lives in `crossref-bib-parse.ts` (not the server-only `crossref.ts`) so it's unit-testable, matching the `*-parse.ts` convention. `crossref.ts` maps each raw CrossRef item to a `BibCandidate` (type, assembled title, resolved year, author surnames, score); `isAcceptableBibMatch(candidate, pastedText)` accepts only when **all** hold: (1) `type` is `journal-article` or `proceedings-article` (the two the citation builders shape correctly — a `book-chapter`/`posted-content`/`dataset` hit is dropped); (2) most of the candidate title's own meaningful words actually appear in the pasted text ("does the text contain this title?" — ≥ 0.8 coverage, or ≥ 0.95 with no corroboration); (3) CrossRef relevance `score` over a bar (≥ 50 corroborated, ≥ 70 not). A matching 4-digit year OR a matching author surname in the pasted text counts as corroboration and lowers bars (1)/(3); a very short/generic title ("Editorial", "Introduction") needs **both** signals regardless. Confirmed against the live API: the real "Stochastic Parrots" query returns the correct proceedings-article at score ~67 (clears the corroborated bar with the pasted author + year), and the next two hits are a `posted-content` preprint (~35) and an unrelated `book-chapter` (~33) — both rejected on type before score even matters.
- **`looksLikeSecondarySourceReference()` (same parse file)** is a cheap pre-filter in `aiExtractFromPastedText`: skip the CrossRef search entirely when the pasted text is clearly a primary legal source — a medium-neutral citation (`[YYYY] COURT N`), a law-report citation (`(YYYY) V ABBR`), or a jurisdiction bracket (`(Cth)` etc.). CrossRef indexes neither cases nor statutes, so a search there would at best waste a call and at worst surface an unrelated article. High-precision markers only, so a genuine journal/conference reference is never excluded. Verified live: pasting "Mabo v Queensland [No 2] (1992) 175 CLR 1" skips CrossRef and produces the correct case citation; pasting "Emily Bender … 'On the Dangers of Stochastic Parrots …' 2021" matches CrossRef, fills authoritative fields, and shows the notice banner with the CrossRef note and verify link.
- **Scope, deliberately:** journal/conference only. Books aren't handled (no builder), and cases/legislation have no title-searchable API. This is a quality upgrade to one input mode, not a general feature — and it makes the paste path *faster* in the matched case (a ~2.5s CrossRef round-trip vs ~8s for the model parse), a happy side effect.
- **A `verifyUrl` on the match (not in the citation).** `AutofillResult` gained an optional `verifyUrl`, set by `fetchCrossRefByBibliographic` to `https://doi.org/<DOI>` (resolves to the publisher's landing page). It is **not** added to the citation, and there is deliberately no `url` field on `JournalFields`/`ResearchPaperFields`: AGLC4 r 5.1 / r 7.2 cite the print form of a work that has a volume/issue/page (which a CrossRef match essentially always has), with no URL — a URL belongs only on a genuinely online-only article (r 5.6), a manual-entry edge case. So the DOI link is purely a verification aid for the fuzzy match, and the citation output is unchanged. It renders in the autofill notice banner (below).
- **Page copy caught up with the feature.** `/generate`'s subtitle used to describe manual entry only ("Select a source type, fill in the details…"); it now names the autofill path and mirrors the three output panel titles exactly ("…the footnote citation, subsequent reference, and bibliography entry"). `AutofillBar`'s single dense grey helper paragraph was broken up: (1) the CrossRef-match hint moved *into the paste `<textarea>`'s placeholder* as a second line ("Note: When pasting journal or conference details, Pinpoint tries to match it to a verified record and links that source for you to check.") — a hint under the box read as applying to the whole autofill area, so it now lives in the box it describes; the textarea went `rows={2}` → `rows={4}` to show it, and the PDF square's hardcoded height was re-measured (104 → 144px) to stay flush with the left column; (2) the accuracy caveat, pulled out and made prominent — amber (`text-amber-700`), medium weight, with a warning-triangle icon — "Automated extraction can get things wrong — always check the result against the actual source before relying on it."; (3) the privacy line moved off the always-visible stack entirely — it's now the PDF square's hover `title` ("Upload or drop a PDF — it's read in your browser and never uploaded to our servers"), and the loading line during a PDF upload reads "Reading the PDF in your browser…". The "Drag a PDF onto the square, or click it to browse" instruction was dropped; the square button labels itself ("Upload PDF", "Drop it here" on drag-over) with `aria-label`/`title` for the affordance.
- **The post-autofill feedback stack moved out of `AutofillBar` into a notice banner in `Generator`.** After an autofill, `AutofillBar` used to stack, under its own input: a "Fields filled ✓ · Please review fields" row, the "Matched to '<full title>' … via CrossRef" note, and the verify link — on top of the two always-on guidance lines. That was a wall of text right where the student was trying to read. Now `AutofillBar` shows only a brief auto-clearing "Fields filled ✓" toast (2s) plus the one always-on caveat; everything actionable — a "check the fields against the source" prompt whenever the result wasn't high-confidence, the CrossRef note, the verify link — rides through `onAutofill` into `Generator`'s `autofillNotice` state and renders as a slim amber banner (with a dismiss ×) directly above the source-type selector, i.e. right above the form it's about. The banner clears when a new autofill starts (same effect that clears a stale warning) or on dismiss. A high-confidence result with no note produces no banner at all. The CrossRef note reads "Source identified from CrossRef: ‘<work title>’ — a best guess, not an exact-identifier lookup." — the title is named (it's the clearest confirmation of *which* work matched) and styled AGLC4-wise: typographic single quotation marks ‘ ’ around it, since AGLC4 quotes a work's own title rather than italicising it. `BarStatus` lost its now-unused `'partial'` member. Pasted text is also **not** cleared from the box after a successful extract (`runPasteText` used to blank it) — the student may want to re-read it against the filled fields or tweak and re-run.

## Legislation jurisdiction: an explicit "unknown", never a default or a carry-over

`LegislationFields.jurisdiction` gained a third value, `'unknown'`, alongside the 8 real codes and `'none'` (the latter still means "deliberately no bracket", ie the bare Commonwealth `Australian Constitution`, r 3.6). `'unknown'` is the "not selected yet / autofill couldn't determine it" state.

- **`mapFieldsToSourceType`'s `'legislation'` case now falls back to `'unknown'`, not `'Cth'`**, when `normalizeJurisdiction` can't match what the model returned. Pasted text like "Weapons Act 1990" gives the model nothing to go on, and silently citing it as `(Cth)` — a real Queensland Act — is exactly the kind of confident-but-wrong output to avoid. The system prompt now also tells the model to leave `jurisdiction` empty rather than guess `'Cth'` or infer it from the Act's subject matter.
- **`jurisdiction` was added to `Generator.tsx`'s `CLASSIFICATION_KEYS.legislation`** so it's never protected by touched-field carry-over — a fresh autofill always reflects the new Act's own jurisdiction (or `'unknown'`), never keeps whatever the student picked for a previous, unrelated citation. Not a "what kind of source" classifier like the other `CLASSIFICATION_KEYS` entries, but it needs the same never-carried-over treatment because a stale jurisdiction is a silent citation error. `BLANK_LEGISLATION_FIELDS.jurisdiction` is `'unknown'` too (the demo `DEFAULT_LEGISLATION_FIELDS` stays `'Cth'` — that's the pristine "Privacy Act 1988 (Cth)" preview).
- **`generateLegislationCitation` renders no jurisdiction bracket for `'unknown'`** (same as `'none'`), and **`getMissingFieldsWarning` flags `'Jurisdiction'`** when it's `'unknown'` (it never did before — the old comment "jurisdiction is never missing" is gone). So the citation is honestly incomplete and the amber warning says "Missing from this citation: Jurisdiction."
- **`validator.ts`'s legislation rule text was told** that an `'unknown'`/empty jurisdiction means the missing bracket is deliberate (surfaced to the student separately) — do not add one, guess one, or flag its absence. Verified live: a jurisdiction-less `Weapons Act 1990` citation comes back "AGLC4 check passed ✓", not "Corrected" with a `(Cth)` added.
- **`LegislationForm.tsx`** shows `'unknown'` as a first `<option>` labelled "Select jurisdiction…", distinct from "None (eg Australian Constitution)".

## Dev workflow

- Port 3000 is occupied by an unrelated project in this environment — always run `npm run dev -- -p 3001`.
- Full verification loop after any change: `npx tsc --noEmit`, `npx next lint`, `npx vitest run`, `npm run build` (the build step matters more than usual here — it's the only thing that catches the Terser/pdfjs-dist issue above), then a live check via the browser.
- To test file upload flows without a real OS file picker: use `javascript_tool` to construct a `File` via `fetch()` + `DataTransfer`, assign it to the file input, and dispatch a `change` event. Cross-origin PDFs will fail with CORS from the browser context (this is correct browser behaviour, not a bug) — for a controlled test PDF, drop it in `public/` temporarily and fetch it same-origin, then delete it afterwards.
- To inspect what a client-side fetch actually sends (eg confirming the PDF file itself never reaches the server), wrap `window.fetch` before triggering the action and log the captured request bodies — more reliable than reading network-panel summaries for this kind of privacy verification.
